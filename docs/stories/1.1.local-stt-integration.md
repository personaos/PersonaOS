# Story 1.1: Local STT Integration (Whisper.cpp)

## Status
Completed

## Story
**As a** PersonaOS user,
**I want** to speak to PersonaOS and have my speech converted to text using local Whisper.cpp,
**so that** I can interact with the system using voice input while maintaining privacy and offline capability.

## Acceptance Criteria
1. Whisper.cpp integration is implemented in `core/sst/` directory
2. Speech-to-text conversion works offline without external API calls
3. Audio input is captured from system microphone
4. Converted text is passed to existing intent processing pipeline
5. STT can be enabled/disabled via configuration
6. Multiple audio input formats are supported (WAV, MP3, etc.)
7. Real-time streaming STT processing is implemented
8. Error handling for audio capture and conversion failures

### File Locations and Project Structure
[Source: CLAUDE.md#core-architecture]
- **Primary STT implementation**: `core/sst/whisper_stt_handler.py`
- **Audio utilities extension**: `core/audio.py`

### Integration Points
[Source: PersonaOS_Spec.md#runtime-workflow]
- **Input Flow**: Audio Input → STT → Intent Classification → Safety Validation → LLM/Tools
- **Existing Intent Pipeline**: `core/intent/intent_processor.py` already handles text input
- **Configuration System**: `core/config.py` provides centralized config management
- **LLM Integration**: Multi-backend system ready to receive processed text

### Technology Stack Requirements
[Source: CLAUDE.md#key-components]
- **Python 3.10+** - Current project requirement
- **Whisper.cpp Python bindings** - For local STT processing
- **Audio capture library** - pyaudio or similar for microphone input
- **Existing logging system** - Use loguru as established in project guidelines

### Technical Constraints
[Source: PersonaOS_Spec.md#goals-philosophy]
- **Local-first approach** - No external API dependencies, fully offline
- **Privacy-focused** - All processing must remain on local hardware
- **Modular design** - STT component must be pluggable and replaceable
- **Configuration-driven** - All features must be configurable via .env

### Testing Standards
[Source: CLAUDE.md#development-guidelines]
- **Testing Framework**: Follow existing testing patterns in the project
- **Unit Testing**: Test individual STT handler methods
- **Integration Testing**: Test STT → Intent pipeline integration
- **Mock Testing**: Use mock audio input for consistent testing
- **Performance Testing**: Ensure STT processing doesn't block main thread

### Security Considerations
- Audio data should not be stored unless explicitly configured
- STT processing should respect existing privacy settings
- Error messages should not expose sensitive system information

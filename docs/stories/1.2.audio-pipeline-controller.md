# Story 1.2: Audio Pipeline Controller

## Status
Draft

## Story
**As a** PersonaOS user,
**I want** a seamless voice conversation controller that orchestrates STT → Intent Processing → LLM → TTS flow,
**so that** I can have natural voice conversations with PersonaOS while maintaining all existing safety validations and tool execution capabilities.

## Acceptance Criteria
1. Audio pipeline controller manages complete voice conversation workflow
2. Controller integrates STT output with existing intent processing pipeline
3. Voice conversations maintain compatibility with existing CLI and web interfaces
4. All existing safety validation and tool execution features work via voice
5. Audio conversation state is properly managed (listening, processing, responding)
6. Voice pipeline can be enabled/disabled independently of other interfaces
7. Error handling and fallback to text-based interaction when voice fails
8. Performance optimization ensures voice processing doesn't block other interfaces

## Dev Notes

### Previous Story Insights
**Dependency**: Requires Story 1.1 (Local STT Integration) to be completed first for STT functionality.

### Current System Architecture
[Source: PersonaOS_Spec.md#runtime-workflow]
- Existing workflow: [User Input: CLI/Audio] → Input Parsing → Intent Classification → Safety Validation → LLM/Tools → Response
- Voice pipeline extends this by adding STT at input and TTS at output while preserving all intermediate processing
- Current intent processing pipeline in `core/intent/` is fully implemented and ready for voice integration

### File Locations and Project Structure
[Source: CLAUDE.md#core-architecture]
- **Primary controller**: `core/voice/voice_pipeline_controller.py` (new directory)
- **Integration points**: `core/main.py`, `core/intent/intent_processor.py`
- **Configuration**: `core/config.py` extensions
- **Audio utilities**: `core/audio.py` (shared with STT implementation)

### Integration Points
[Source: CLAUDE.md#intent-processing-safety]
- **Intent Processing**: `core/intent/intent_processor.py` - Main pipeline entry point
- **Safety Validation**: `core/intent/safety_validator.py` - Must be preserved for voice
- **Tool Execution**: `core/tools/` - Plugin system must work via voice
- **LLM Integration**: `core/llm/llm_handler.py` - Multi-backend system ready for voice integration

### Technology Stack Requirements
[Source: CLAUDE.md#key-components]
- **Threading support** - For non-blocking voice processing
- **State management** - Track voice conversation lifecycle
- **Configuration system** - Extend existing `core/config.py` patterns
- **Error handling** - Follow existing error handling patterns in intent processing

### Technical Constraints
[Source: PersonaOS_Spec.md#key-design-principles]
- **Separation of intent and execution** - Voice input must go through same intent validation
- **Extensibility over complexity** - Voice controller should be modular and replaceable
- **Human-in-the-loop** - Safety validation must be preserved for voice-triggered tools
- **No daemon lock-in** - Voice pipeline runs within existing user-space application

### Existing Component Integration
[Source: CLAUDE.md#llm-integration]
- **LLM Manager**: `core/llm/llm_handler.py` supports hot-swapping backends
- **Memory System**: `core/llm/memory.py` with conversation threading
- **Web UI Architecture**: FastAPI backend must remain unaffected by voice processing
- **Tool System**: `core/tools/tool_registry.py` provides plugin architecture

### Threading and Performance Considerations
- Voice processing must not block CLI or web UI interfaces
- STT processing should run in separate thread from main conversation loop
- TTS output should be asynchronous to avoid blocking user input
- State management must be thread-safe

### Testing Standards
[Source: CLAUDE.md#development-guidelines]
- **Unit Testing**: Test voice controller state transitions and error handling
- **Integration Testing**: Test complete voice pipeline with mock components
- **Performance Testing**: Ensure voice processing doesn't degrade other interfaces
- **Thread Safety Testing**: Verify concurrent operation with CLI/web interfaces

### Security and Privacy Considerations
- Voice conversations must pass through existing safety validation
- Audio processing should respect existing privacy settings
- Voice session data should integrate with existing memory encryption
- Tool execution via voice must maintain existing security constraints
